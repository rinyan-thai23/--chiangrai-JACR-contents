# 情報源アクセス手段リスト

最終更新: 2026-09-09

このファイルは、北タイ・チェンライの情報収集に使いたい各情報源について、**本セッションの実行環境から直接アクセスできるか**を実際に検証した記録と、その代替手段をまとめたものです。ポリシーやアクセス可否は環境の設定変更で変わりうるため、次回検証時は本ファイルを上書き更新してください（検証手順は末尾参照）。

## 1. まず結論: 「サイトごとの許可・不許可」ではなかった

当初は「Facebookはブロックされるがこのニュースサイトは通る」といった**サイト単位の差**を想定して調査した。実際に検証すると、そうではなく、**本セッションの環境が開発用ドメイン（npm・pypi・Anthropic API等）以外への外部アクセスを種類を問わずほぼ全面的に拒否する設定**になっていることが判明した。

検証結果（2026-09-09、`WebFetch`および`curl`で直接疎通確認）:

| 対象 | 結果 |
|---|---|
| Facebook（www / m.facebook.com） | ブロック（EGRESS_BLOCKED） |
| Instagram | ブロック |
| X（Twitter） | ブロック |
| YouTube | ブロック |
| Google本体・Google News・Wikipedia | ブロック |
| タイ政府系（.go.th：気象庁 tmd.go.th、県庁 chiangrai.prd.go.th 等） | ブロック |
| タイ大手紙（Thairath, Sanook, Nation Thailand, Bangkok Post, The Thaiger） | ブロック |
| チェンライ地域密着サイト（ChiangraiFocus, NayYai, Chiang Rai Times） | ブロック |

`curl`で直接叩いた場合もプロキシ側のログに `gateway answered 403 to CONNECT (policy denial)` とだけ記録され、www.google.com のような一般的な大手サイトすら通らない。**唯一機能しているのは `WebSearch` ツール**（Anthropicのサーバー側で検索・要約を行い、結果だけがこのセッションに返る方式のため、このegressプロキシを経由しない）。

## 2. 有料IPプロキシ/VPNサービスの検討結果

**現状のセッション構造では機能しない見込み。** このセッションの全アウトバウンド通信は強制的にこのegressプロキシを経由する。プロキシサービス自体のドメイン・IPへの接続要求も、ホワイトリスト外である以上、同じように拒否される。つまり「プロキシの奥にもう一段プロキシを立てて回り込む」という構造がそもそも成立しない。

有効にする唯一の道は、**このセッションが動いている実行環境（Environment）自体のネットワークポリシーを変更すること**。これはリポジトリのコードや会話の中では変更できない、Claude Code on the web側の環境設定の話になる（ドキュメント: https://code.claude.com/docs/en/claude-code-on-the-web ）。

**推奨する順番**:
1. まず環境のネットワークポリシーを「フルアクセス」寄りに変更できないか確認する（無料でできる範囲）。
2. それでも特定サイトだけ弾かれる場合に、初めて有料プロキシ／専用の許可ドメイン追加を検討する。
3. ポリシーを変えたら、本ファイルの検証をやり直して更新する。

## 2-2. Apify等スクレイピングツールの検証結果とブリッジ案（アイデア止まり・API連携は保留中）

ユーザーが契約しているApify（クラウド型スクレイピングサービス）を使えないか、2026-09-09に追加で検証した。

**検証結果**: `api.apify.com` / `console.apify.com` への直接アクセスは他の外部サイトと同様にブロック。一方で、以下は到達性が確認できた。

| 対象 | 結果 |
|---|---|
| api.apify.com / console.apify.com | ブロック |
| api.notion.com / slack.com API / hooks.zapier.com / hook.*.make.com | ブロック |
| api.github.com | 到達可能（HTTP 200） |
| raw.githubusercontent.com | 到達可能（HTTP 301） |
| googleapis.com系（Drive/Gmail等のルート） | 到達可能（HTTP 404＝接続はできている、パス指定の問題） |

つまり任意の外部APIを直接叩く経路はやはり塞がっているが、**このセッションに元々搭載されているファーストパーティのコネクタ（Google Drive・Notion・Slack）は、このegressプロキシとは別チャネルで機能している**ため、そこを中継地点にできる可能性がある。

**ブリッジ案（アイデアのみ、未実装・未検証）**:
1. Apifyの実行結果をGoogle Sheets/Driveに自動出力（Apify標準のGoogle連携機能） → こちらは`Google Drive`コネクタで読む
2. Apifyの実行結果をNotionデータベースに書き込む → こちらは`Notion`コネクタで読む
3. Apifyの実行結果をSlackチャンネルに通知 → こちらは`Slack`コネクタで読む
4. Apifyの実行結果をGitHub（このリポジトリ）に直接コミットする仕組みを組む → こちらは通常の`git pull`で読む（GitHubへの到達性は本セッションの通常のcommit/push操作で実証済み）
5. ネットワーク制限のない別環境（ローカルPCや別のClaude Code環境）でApifyを叩き、結果をこのリポジトリにコミットしてもらう

**現状の位置づけ**: 2026-09-09時点でユーザーの意向により、API/コネクタ経由の自動連携は一旦保留。上記はアイデアの記録として残すのみで、実装・実データでの検証はしていない。着手する場合は次回の実行記録に検証結果を追記すること。

## 3. ポリシー変更後の見込み（参考・未検証）

ネットワークポリシーが変わった場合に、各情報源がどの程度取得しやすくなりそうかの見立て。あくまで一般的なサイト構造からの予測であり、実際にポリシーが変わった時点で再検証が必要。

| 情報源 | 現状 | ポリシー変更後の見込み | 理由・備考 |
|---|---|---|---|
| Facebook公開ページ・グループ | ブロック | △ 難しい可能性が高い | ログイン要求・JS描画前提のSPA・bot対策が強い。非公開グループはそもそも規約上も取得不可 |
| X（Twitter） | ブロック | △ 難しい | 同上。まとまった取得にはAPI契約が事実上必須 |
| Instagram | ブロック | △ 難しい | 同上 |
| YouTube | ブロック | ○ 字幕・概要欄レベルなら中程度 | 動画そのものでなく概要・字幕テキストなら取得しやすい可能性 |
| ChiangraiFocus.com 等チェンライ地域密着サイト | ブロック | ◎ 取得しやすい見込み | 静的HTMLの一般掲示板・ニュースサイトで、bot対策が弱ければ問題なく読める |
| Chiang Rai Times / Thairath / Sanook / Nation Thailand / Bangkok Post 等 | ブロック | ◎ 取得しやすい見込み | 一般ニュースサイト。現状もWebSearch経由の要約では情報を取得できている |
| タイ政府系（.go.th：気象庁・防災局・県庁） | ブロック | ◎ 取得しやすい見込み | 静的な広報ページが中心 |
| Google News RSS / 各紙RSSフィード | ブロック | ◎ 最有力候補 | 構造化されており軽量。ポリシー変更後はここを優先的に組み込みたい |

凡例: ◎取得しやすい / ○条件次第 / △引き続き困難が見込まれる

## 4. 当面（ポリシー未変更の間）の運用結論

- 収集手段は引き続き **`WebSearch`による複数ソースのクロスチェック**（[../README.md](./README.md)「実行内容」節、[runs/2026-09-09-launch.md](./runs/2026-09-09-launch.md)参照）を正式な方式とする。
- 「Facebookグループの現地生情報を直接見たい」という当初の狙いは、現状のセッション内では実現できない。ポリシーが変わっても、SNS勢は規約・bot対策の壁が別途あるため、**まずRSS・静的ニュースサイト系から着手するのが現実的**。
- 有料プロキシの契約は、環境側のポリシー変更を試してから判断する（先に無料の選択肢を潰すのが優先）。
- Apify等のAPI/コネクタ経由の自動連携（「2-2」節）は、2026-09-09時点でユーザーの意向により一旦保留。

## 5. 再検証の手順（次回このファイルを更新する人向け）

1. 各URLに対して`WebFetch`を実行し、`EGRESS_BLOCKED`か成功かを記録する。
2. 疑わしい場合は `curl -sS -o /dev/null -w "HTTP:%{http_code}\n" --max-time 10 <URL>` と `curl -sS http://127.0.0.1:44283/__agentproxy/status` の `recentRelayFailures` で403の詳細を突き合わせる。
3. 結果を本ファイルの表に反映し、冒頭の「最終更新」日付を更新する。
